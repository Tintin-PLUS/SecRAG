# 端侧知识库技术选型测试方案（SecRAG）

> 面向对象：性能验证负责人（课题第 3 项交付物《端侧知识库技术选型对比分析报告》的测试前置）。
> 目标对象：Windows x86_64 PC、CPU-only、Tauri v2 + React + Rust + SQLite + Python SentenceTransformer Sidecar。
> 本文是"测试方案/操作手册"，与 `docs/guides/PERFORMANCE_TESTING.md` 互补：前者解决"框架内置微基准怎么跑"，本文解决"为了做技术选型，应该完整地测哪些维度、用什么定义、怎么记录、结论怎么判读"。

---

## 1. 测试目标与范围

### 1.1 测试目的

端侧知识库的选型不是单点比较，而是**一条完整数据链路**的性能与资源权衡：

```
扫描/导入文档 -> 解析 -> Chunk(切分) -> Embedding(向量化) -> 向量入库 -> 语义检索(Top-K) -> RAG拼装 -> [可选外部LLM]
```

技术选型需要在以下四个可替换点上做出决策，因此测试方案必须**逐层解耦、分别计量**，并保留"更换某层不影响其它层"的对比能力：

| 可替换点 | 现有实现 | 测试关心的替代候选 |
|---|---|---|
| 文档切分策略 | `FixedSizeChunker`（默认 500 字符 / 80 overlap）；`embedding-test` 用结构切分 | 按字符数、按段落/标题结构、不同 overlap、自定义切分 |
| Embedding 模型 | Python Sidecar：`bge-small`(512) / `m3e-base`(768) / `bge-m3`(1024) | 三者对比；未来其它轻量模型 |
| 向量存储 | `SqliteVectorStore`（SQLite BLOB + Rust cosine，O(N·D) fallback） | `sqlite-vec`（必做对照），或其它嵌入式向量库 |
| 检索策略 | 纯 cosine Top-K（local-kb）；`embedding-test` 为 BM25+向量 RRF 混合 | 是否为证券场景引入混合检索（本方案记为"未定/后续"） |

测试不追求"分出一个绝对冠军"，而是要回答：**在离线、合规、低配置 PC 约束下，各方案在检索效果、速度、内存、磁盘占用、增量更新效率上的真实取舍。**

### 1.2 测试边界（明确不做 / 只做结论性说明）

以下事项**不在本次实测范围**，避免业余化：

- **不对比 Electron**：未制作可运行的 Electron 对照程序，不编造其性能数字；仅做官方资料层面的框架对比。
- **只用 CPU**：固定 CPU 推理，不谎报 GPU；记录模型实际运行设备。
- **不做 RAG"回答质量"（faithfulness / groundedness）评测**：需要 LLM 或人工精标，且当前 RAG 走外部 DeepSeek，涉及出域。本方案只测"检索质量 + 链路时延"，RAG 答案质量记为"待数据分级后另测"。
- **不测网络 / 分布式 / 服务型向量库（Milvus、Qdrant 等）**：与端侧离线定位冲突。
- **不混入 Mock Embedding 的质量指标**：Mock 只用于链路联调，绝不写入检索效果结论。

### 1.3 可替换点之间的约束

- 每个测试组合必须固定 `knowledge_base` 的 `chunk_strategy`、`chunk_size`、`chunk_overlap`，不再中途改动。
- 每个 Embedding Profile 由 `(model_id, model_version, dimension, config_hash)` 唯一确定；换配置必须升 `config_hash`，旧 Index 需重建，禁止在同一 Profile 混用。
- 不同模型/维度必须在**完全相同的语料、切分、题集**上比较，否则结果不可比。

## 2. 被测系统与环境基线

### 2.1 组件与版本（每轮必填）

| 项目 | 值 | 来源 |
|---|---|---|
| 操作系统 | Windows 10/11 x86_64 | `winver` |
| 电源模式 | 高性能 / 平衡（如实记录，正式对比建议固定为同一档） | 设置 |
| CPU / 核心 / 线程 | 型号、物理核/逻辑核 | `Get-CimInstance Win32_Processor` |
| 内存 | 总量 / 当前空闲 | `Get-CimInstance Win32_ComputerSystem` |
| Rust | `rustc -V`，目标 `x86_64-pc-windows-msvc` | `rustc -V` |
| Node | `node -v` | `node -v` |
| Python | `python -V`；`sentence-transformers`、`torch` 版本 | `.venv` 内 `pip list` |
| 是否接电 | 是 / 否 | 人工 |
| 当时温度/降频 | 如需精确可记录 HWiNFO | 可选 |

> 同一台机器上做多次对比时，机器不变，但**软件版本、后台进程、散热状态会变**。因此每一次正式结果前面必须带上本表，不能只留一次。

### 2.2 进程边界（内存统计口径）

端侧应用由多个进程组成，内存必须**分进程**统计，不能只写"应用占用 X MB"：

- `local-kb.exe`（Rust / Tauri 主进程）
- WebView2 子进程（`msedgewebview2.exe`，可能多个）
- `python.exe`（Embedding Sidecar）
- （可选）`node.exe` / Vite，仅开发态存在，生产态不统计

### 2.3 数据目录隔离

测试一律使用**独立数据目录与数据库**，禁止污染业务库 `local-kb/data/local-kb.sqlite3` 和 `embedding-test/data/knowledge.db` 之外的任何数据。建议约定：

```
local-kb/data/microbench/<run_id>/   # 框架内置微基准（内存库，本就隔离）
local-kb/data/experiments/<run_id>/  # 端到端资源与存储占用测试
embedding-test/data/<run_id>/        # 检索质量评测
```

`<run_id>` 建议 `yyyyMMdd-HHmmss`。实验目录与原始 CSV 不上传 Git。

## 3. 测试数据与语料（可复现）

### 3.1 质量评测语料（检索效果用）

- 复用 `embedding-test/test_docs/` 的 12 份模拟金融资料 + `eval/test_queries.json`（34 题），作为**默认小语料基线**。
- 如需更有区分度，可扩充到约 30 份差异化资料 + 60 题（50 题有答案、10 题无答案），并**人工标注证据段落**；自动生成数据只支撑"模拟场景实验"，不代表真实业务准确率。
- 题集分"调参集"与"测试集"，**禁止混用**。
- 标注 = 人名/机器 + 是否人工复核；证据位置用稳定标识（如章节标题），不用数据库 UUID。

### 3.2 性能/资源测试语料（速度与资源占用）

构造固定规模的数据集，用于测量吞吐、时延、内存、磁盘：

| 数据集 | 规模 | 用途 |
|---|---|---|
| Chunk 100 | 100 条向量 | 微基准下限 |
| Chunk 1,000 | 1,000 条向量 | 中等规模 |
| Chunk 10,000 | 10,000 条向量 | 端侧规模压力 |
| 文档级 | 若干份固定长文档 | 切分策略、增量更新 |

> 1,000 / 10,000 条用于测速度，**不要把重复扩容数据当作质量评测数据**。质量与性能两组数据相互独立。

### 3.3 固定的测试问题集（质量 + 时延共用）

- 质量评估：`test_queries.json`（需人工核对的 are 相关标准）。
- 纯时延评估：从题集中抽取约 50 条，**重复执行（如每条 20 次）** 用于测 P50/P95；重复执行只增加耗时样本，不增加质量评测的独立样本数。

## 4. 通用测试指标定义

这一节是本方案的核心，覆盖**一般性技术测试指标类型**。每类指标给出：定义、单位、采集方法、口径要点、本节**包含/排除**的判断。

### 4.1 检索质量指标（效果类）

| 指标 | 定义 | 单位 | 说明 |
|---|---|---|---|
| **Recall@k** | 返回前 k 条中命中相关条目的数量 / 该 query 的全部相关条目数 | 0~1 | 检索"找全"能力 |
| **Precision@k** | 前 k 条中相关条目数 / k | 0~1 | 检索"找得准"能力 |
| **Hit@k** | 前 k 条中至少一条相关的 query 比例 | 0~1（%） | "能否找到答案"（图 2 已用 Hit@3） |
| **MRR@k** | 第一条相关条目排名的倒数，对全部相关为 0 的样本记 0，取均值 | 0~1 | "答案排第几"（图 2 已用 MRR@3） |
| **nDCG@k** | 折损累积增益，按相关度分级归一化 | 0~1 | 更精细的排序质量（需相关度分级标注） |
| **MAP** | 平均精度均值（跨多 query） | 0~1 | 综合排序质量 |

**取舍判断**：
- **必测**：`Hit@k`、`MRR@k`（图 2 已有，必须延续以便趋势可比）、`Recall@k`（端侧资料找全很重要）。
- **建议增强**：`nDCG@k`、`Precision@k`、`MAP`。若题集只有"相关/不相关"二元标注且不评分级，`nDCG` 弱化为 `binary nDCG`（等同 Recall-graded），此时优先报 `Precision@k`/`MAP` 更有意义。
- 相关判定必须写明：图 2 / 现有 `eval_search.py` 用的是"含 `must_contain` 全部词 + 至少一个 `any_of` 词"的**关键词自动规则**，**不等于人工审核**。正式报告须注明该局限，并在可行时抽样人工复核。

### 4.2 延迟指标（时延类）

| 指标 | 定义 | 单位 | 口径要点 |
|---|---|---|---|
| **单查询时延（end-to-end search）** | 从发出 query 到拿到 Top-K 结果 | ms | 含 query 向量化 + 检索 + 通信 |
| **检索阶段时延** | 仅向量库 search 返回 | ms | 分离存储层贡献 |
| **首 Token 时延（TTFT，Time To First Token）** | 端到端链路中，从发出提问到收到**第一个生成 token** 的耗时 | ms | 用户体感关键指标；仅在有 LLM 的 RAG 场景可测 |
| **端到端 RAG 时延** | query → retrieval → context 拼装 → LLM 首/全 token | ms | 受外部 LLM 网络影响，需离线边界 |
| **冷/热态** | 冷 = 首次加载（模型未驻留）；热 = 模型已驻留 | — | 必须区分，二者差异极大 |

**关键统计口径**：
- 每个场景**预热 3 次**，正式运行**至少 10 次**，报告 **P50 / P95 / P99 / min / max / 均值**。
- 给受众解释：P95 = "约 95% 的请求比这个时间快"。
- 冷启动与热态**分开记**，不混淆；模型加载时间单独记（见 4.4）。

**取舍判断**：
- **TTFT 必列**（用户明确点名，且是 RAG 交互的核心体感指标）；但当前 RAG 走外部 DeepSeek，实际意义受网络与合规限制，因此在本文中 TTFT 归入"RAG 链路（可选外部 LLM）"一节，**缺省只测到检索层**，并把"LLM 未配置/不出域"作为边界写清楚。

### 4.3 吞吐量指标（吞吐类）

| 指标 | 定义 | 单位 | 用于哪层 |
|---|---|---|---|
| **QPS（queries/s）** | 每秒完成的检索请求数 | queries/s | 向量检索 |
| **texts/s** | 每秒向量化的文本条数 | texts/s | Embedding 批量 |
| **tokens/s** | 每秒处理 token 数 | tokens/s | Embedding 批量（更贴近模型真实负载） |
| **chars/s** | 每秒处理字符数 | chars/s | 解析/切分 |
| **vectors/s** | 每秒入库向量数 | vectors/s | 向量入库 |
| **docs/s** | 每秒处理文档数 | docs/s | 导入/切分 |

**口径要点**：
- 吞吐与 batch size 强相关：Embedding 必须测 `batch = 1/8/16/32/64` 的吞吐曲线，并记录**峰值 batch**。
- 吞吐测量必须在**稳态（热态）**下进行；冷启动的吞吐不作为稳态值。
- Python Sidecar 在内存中驻留一次模型，连续请求才能测出真实吞吐；**每个模型独立启动服务进程再测**，避免前一个模型常驻内存拖累后一个模型。

### 4.4 资源与体积指标（资源类）

#### 4.4.1 内存（RAM）

| 指标 | 定义 | 采集 |
|---|---|---|
| **Working Set** | 物理内存驻留集 | `Get-Process` 的 `WorkingSet64`，按进程 |
| **Private Bytes** | 私有提交内存 | `PrivateMemorySize64` |
| **峰值（Peak）** | 测试期间最大驻留 | 定时采样取 max |
| **基线/稳态** | 空闲时、测试结束后回落值 | 测试前中后三段采样 |

采集建议：用 PowerShell / Performance Monitor 以 **500 ms** 间隔对 `local-kb`、`msedgewebview2`、`python` 三个进程分别采样，记录 `CPU` 累计差分、`WorkingSet64`、`PrivateMemorySize64`。原始 CSV 放性能负责人自己的测试目录。

#### 4.4.2 CPU

| 指标 | 定义 | 说明 |
|---|---|---|
| **平均 CPU%** | 测试期间进程 CPU 占比均值 | 分进程采集 |
| **P95、峰值 CPU%** | 95 分位与峰值 | 判断是否触发降频 |

#### 4.4.3 存储占用（磁盘）

| 项目 | 说明 |
|---|---|
| **数据库体积** | 不同维度（512/768/1024）、不同规模（100/1k/10k）下 `*.sqlite3` 的文件大小变化 |
| **每向量字节** | 单条向量占用的存储 = 维度 × 4 字节（f32）+ 元数据/索引开销 |
| **模型体积** | `models/` 下各模型目录大小 |
| **运行环境体积** | `.venv` + Python 依赖 +（未来）EXE 安装包体积 |
| **离线可用体积** | 模型 + Python 依赖 + 数据库 + 应用，**不能只统计 EXE** |

**关键点**：维度直接决定存储与检索成本（512 vs 768 vs 1024）。`bge-m3` 维度 1024，单条向量原始 4 KB，但模型 ~2.3 GB，需在"效果提升"与"体积/内存/速度代价"之间权衡——这正是图 2 数据要回答的问题之一。

#### 4.4.4 加载时间

| 指标 | 定义 |
|---|---|
| **模型加载时间（冷）** | 首次索引请求开始到模型就绪（日志出现 `loaded <model>` 或首批请求返回） |
| **Sidecar 启动时间** | 点击启动到 `/health` 返回协议 1（不含模型加载） |
| **应用冷启动时间** | 双击启动到界面可交互 |

### 4.5 文档切分策略指标

用户明确点名，是选型的核心维度之一。切分策略直接影响：检索质量、chunk 数量、入库体积、检索时延。

**候选策略**（本文建议对比）：

| 策略 | 说明 | 关键参数 |
|---|---|---|
| 固定字符切分 | 按字符数切，`FixedSizeChunker` | `chunk_size`、`chunk_overlap` |
| 段落/标题结构切分 | 按标题、空行段落聚合（`embedding-test` 的 `chunk_by_structure`） | `max_size`、`min_size` |
| 按语义/长度混合 | 长段落再按句读（`。；\n`）断点回退 | 断点候选、min/max |
| token 切分 | 按模型 tokenizer，避免截断 | `max_tokens`、overlap |

**指标**：

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **Chunk 总数 / 平均长度 / 长度分布（min/max/中位）** | 不同策略下切出的块数、长度统计 | 决定入库体积与检索粒度 |
| **切分吞吐（chars/s、docs/s）** | 切分是整个导入链路的一环 | 大语料导入耗时 |
| **重叠率（overlap ratio）** | `overlap / chunk_size` | 过高增大冗余和体积，过低导致语义断裂 |
| **语义完整性 / 信息覆盖** | 上下游质量指标在**不同切分下**的 `Recall@k` / `Hit@k` 变化 | 切分策略的最终收益，必须落到检索质量上 |
| **切分稳定性** | 相同输入多次切分是否一致（确定性） | 决定可复现性 |
| **截断率** | 超长内容被截断的比例及影响 | 长文档、长表格场景 |

> **最重要的结论来源**：切分策略不能只看"切得规不规整"，必须看它**对下游检索质量（Recall/Hit/MRR）和时延/体积的影响**。因此切分测试要与 4.1 质量测试、4.2 时延测试、4.4 体积测试联动。

### 4.6 增量更新与生命周期指标

端侧知识库必须支持文件增/删/改的**最小化更新**，不能整库重建。

| 指标 | 定义 |
|---|---|
| **增量更新时延** | 修改一份固定大小文档，从事件/手动扫描到新 Chunk 写入、旧 Vector 删除、Profile 变 `STALE` 的耗时 |
| **受影响 Chunk 数** | 只重建目标文档的 Chunk，其余不变的数量 |
| **删除级联时延** | 删除文件到 Document/Chunk/Vector 级联清理的耗时 |
| **一致性** | 更新后仅目标文档 Chunk ID 变化，其它文档 ID/Chunk/Vector 不变，Profile 为 `STALE` |
| **一致性校验** | 更新后 `vector_record` 与 `chunk` 的缺失/多余计数 |

## 7. 嵌入式向量库对照实验：sqlite-vec vs fallback（必做）

> 本节为**必做**对照项。目的：回答"当前 SQLite BLOB + Rust cosine 的 O(N·D) fallback 在大规模下是否够用，以及换 sqlite-vec 是否值得"。这是选型结论的重要组成部分，不是加分项。

### 7.1 为什么值得做

当前 `SqliteVectorStore::search` 是 O(N·D)，且每次把**全部**候选 BLOB 读入内存再算 cosine。在 1,000 Chunk 尚可，10,000 Chunk 时延迟与内存上升明显；规模再大或维度升高会放大问题。`sqlite-vec` 作为向量索引可显著降低检索复杂度，但会引入扩展装载/分发/版本兼容问题（本项目文档已说明选择 fallback 的原因）。

### 7.2 实验设计

1. 在 `local-kb/src-tauri/src/vector_store/` 新增 `SqliteVecStore`，**实现既有 `VectorStore` Trait**，不改 Command / Retrieval / Ingest 的 API。
2. Schema migration 创建 vec virtual table；保留 `embedding_profile` 和 `index_state`。
3. 对不同 dimension（64/512/768/1024）建独立 virtual table/partition（或按 sqlite-vec 当前官方能力选择）。
4. Ingest 仍先做 Profile / Chunk / dimension 校验。
5. **完全相同**的向量、问题、相似度规则前提下，比较：读写吞吐、检索 P50/P95、磁盘体积、内存峰值、**召回一致性**（sqlite-vec 与 brute-force cosine 的结果排序差异）。
6. 注意 sqlite-vec 的距离（越小越近）与当前 cosine 相似度（越大越近）的**排序方向转换**。

### 7.3 对照维度

| 维度 | SQLite BLOB + Rust cosine（基线） | sqlite-vec（候选） |
|---|---|---|
| 入库吞吐（vectors/s） | | |
| 检索 P50 / P95（Top-5/10） | | |
| QPS | | |
| 磁盘体积 | | |
| 内存峰值 | | |
| 召回一致性（@10 与基线命中重合度） | | |
| 1,000 / 10,000 Chunk 的延迟曲线 | | |

### 7.4 落地建议

- 本节为**必做项**：优先完成 `SqliteVecStore` 最小适配并做对照；若 `sqlite-vec` 在当前 Windows + Rust 版本下确实无法稳定集成，**保留失败记录及原因**，在报告中标为"调研候选、未完成本地性能验证"——**不允许编造对比结果，也不允许因失败而省略本对照的结论说明**。
- 对照结果必须与基线（SQLite BLOB + Rust cosine）在**相同数据、维度、Top-K、机器矩阵**下分别报告，覆盖后不覆盖 fallback 基线。
- 若实验后仍决定保留 fallback，需在报告中明确"在什么规模下 fallback 仍可接受、超过多少规模需要引入索引"。

## 9. 判读边界与限制

- **CPU-only**：所有数据是 CPU 推理结果；不得推导 GPU 性能。
- **小语料**：34 题 / 12 份资料是小样本，命中率区间估计误差较大，结论只能表达"在该语料下的相对差异"，不宜绝对化。
- **冷/热混淆**：严禁把冷启动时延与热态吞吐混用；报告分开记。
- **关键词自动判定**：与人工审核不等价；有条件时抽样人工核对。
- **离线**：本地请求成功 ≠ 完全离线验证；需在断网环境单独验证（本方案记为"待断网验证"）。
- **模型体积/亿级数据**：10,000 Chunk 只是端侧规模压力，不代表生产级；超过后应重测并讨论是否引入索引（sqlite-vec / HNSW）。
- **维度与存储**：维度翻倍，单条向量原始字节翻倍；耗时、内存、磁盘同步上升，选型必须同时给出"效果-成本"曲线而不是只报一个"最好"。
