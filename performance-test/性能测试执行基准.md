## 0. 目标与主图

**目标**：在一张图上，用"**效率随硬件档位变化**"做纵轴、用"**颜色标质量**"做第三维，直观看：**每个配置在不同硬件档位上效率如何，以及它的质量有多高**。

**主图**：散点/气泡图
- **横轴 x**：硬件档位（分类轴）
- **纵轴 y**：熵权效率分（0–100）
- **颜色**：质量加权分（连续色带 colormap + 右侧 colorbar）
- **大小 / 标签**：配置名

---

## 1. 横轴：硬件档位（分类轴，不是连续量）

| 档位 | 内存 | CPU 核心数 | 说明 |
|---|---|---|---|
| T1 入门 | ≤8 GB | ≤4 核 | 低配，限制最多 |
| T2 主流 | 8–16 GB | 4–6 核 | 多数办公机 |
| T3 进阶 | 16–32 GB | 6–8 核 | 性能较好的分析机 |
| T4 高配 | ≥32 GB | ≥8 核 | 接近工作站 |

> **规则**：档位是**分类/有序类别**，用竖轴虚线区隔；**不要画回归线、不要当连续数字用**、不要据此外推"再高一级就更快多少"。

---

## 2. 纵轴：熵权效率分（0–100，**每档内单独算熵权**）

- 只取**效率类指标**进熵权（见 ③）。
- 每个指标先 **min-max 归一化到 [0,1]**，**成本类（延迟/内存/CPU/磁盘）取反**，统一成"越大越好"。
- **在同一档位内部**算熵权，不跨档位。
- 公式：`p_ij = x_ij / Σ_i x_ij`；`e_j = −(1/ln m)·Σ_i p_ij ln p_ij`；`d_j = 1 − e_j`；`w_j = d_j / Σ d_j`；`效率分_i = 100 × Σ_j w_j × x_ij`。
- 若只用延迟一个指标，熵权退化为直接用延迟（此时无"综合"意义），需在结果里注明。

---

## 3. 颜色：质量加权分（不进熵权）

- 用连续色带（colormap）+ 右侧 colorbar，质量为高 → 暖色、低 → 冷色。
- **质量分 = `w1×Recall@k + w2×MRR@k + w3×nDCG@k`**（各指标先 min-max 归一到 [0,1] 再加权；权重均等/熵权/AHP 均可，须写明）。
- **注意**：质量分**不随硬件变**（同模型 + 同输入，向量是确定性的）。所以**同一配置在不同档位上颜色相同（同质量），只有纵轴效率分数随档位变化**。

## ② 每个散点需要固定值的参数（组内保持不变的"固定项"，决定坐标可比）

管线配置，一次对比里**只允许动一个**，其余固定（见 §5.2）。**散点的"身份"由这五个共同定义**：`Model`、`chunk_size`、`overlap`、`Top-K`、`VectorStore`。

| 对比组 | 固定不变 | 只能变 |
|---|---|---|
| 比模型 | chunk_size、overlap、Top-K、VectorStore | Model |
| 比切分 | Model、Top-K、VectorStore | chunk_size 或 overlap |
| 比 Top-K | Model、chunk_size、overlap、VectorStore | Top-K |
| 比存储 | Model、chunk_size、overlap、Top-K | VectorStore |

> 固定项还包括：**语料 / 题集**。每张图必须写清"固定了什么、只变了什么"。

## ③ 进入熵权法计算的参数（效率指标，纵轴输入）

只有效率类指标进熵权，且必须先归一化 + 成本类取反，再在**同一档位内**算熵权。

- **延迟**：`P50` / `P95` / `P99`（建议用 `P95` 或 `P99` 代表体感）
- **吞吐**：`QPS`、`texts/s`、`tokens/s`、`vectors/s`
- **内存**：整栈峰值内存（Rust `local-kb.exe` + WebView2 `msedgewebview2` + Python Sidecar `python`，**按最坏时点**测，如最大规模建索引 / 最大 batch）
- **CPU**：峰值 / 均值 CPU%
- **磁盘**：占用的磁盘体积（含模型 + 依赖 + 库）

## 4. 质量指标（用于"质量加权分"，**不进熵权**）

方向均为"越高越好"，大多落在 [0,1]。

| 指标 | 含义 | 方向 |
|---|---|---|
| `Recall@k` | 前 k 条命中了多少"该被找到的相关内容"（**找全**能力） | 越高越好 |
| `Precision@k` | 前 k 条里有多少是相关的（**找得准**能力） | 越高越好 |
| `Hit@k` | 前 k 条里**至少一条**相关的提问占比（"能否找到答案"） | 越高越好 |
| `MRR@k` | **第一条**相关结果的排名倒数均值（"答案排第几"） | 越高越好 |
| `nDCG@k` | 按相关度分级、带位置折损的排序质量（"整体排得好不好"） | 越高越好 |
| `MAP` | 平均精度均值，跨多个 query 的综合排序质量 | 越高越好 |

- **主推组合**：`Recall@k + MRR@k`；或**只用 `nDCG@k`**（一个就够）。
- **避免坑**：`Hit@k`、`Recall@k`、`MRR@k` **高度相关**，都平均会重复计权。
- **k 取值**：质量评估固定 `k=3`（与图 2 / `eval_search.py` 对齐）；检索性能另用 `k=5` / `k=10`。

## 补充 A：内存可行性（硬门槛，先于效率分）

- 一个配置能跑，要求**整栈峰值内存远小于物理内存**：`peak_mem × headroom ≤ RAM`，其中 `headroom ≈ 1.5~2`（峰值 ≤ 约 50–66% 物理内存）。
- 峰值按**最坏时点**评估，不能用空载内存。
- 图上对某档位**内存余量不足**的点应**置灰 / 剔除**，不参与该档熵权。

## 补充 B：跨档可比性提醒

- 因为熵权**每档单独算**，纵轴分数是"**档内相对效率**"，跨档位严格说不可直读比较；若需跨档可比，可改用**统一权重**（见完整方案 §8.3），或纵轴直接用 `P95` 延迟 / `QPS` 这类**物理可比**指标。
- 只有本机一台时，只有一个档位是"**实测**"，其余为"**估算**"，图上须标明。
