# 证券 PC 端本地知识库技术选型与轻量化场景验证计划

> 本文以课题《证券 PC 端剧本地知识库应用评估与轻量化场景验证》的课题内容、准入门槛和完成标准为依据。原文件 `性能测试执行基准.md` 保留不变；本文作为更贴近课题验收目标的新执行计划。
>
> 本文是轻量集成验证方案，不是生产容量规划、监管合规认证或大规模向量数据库 benchmark。未经实际执行的数据一律标记为“未测试”，不得用估算值替代实测结论。

---

## 0. 课题定位

### 0.1 核心目标

在 Windows x86_64、CPU-only、离线优先的 PC 环境中，验证采用 Tauri + Rust + 本地 Embedding + 嵌入式向量库建设证券本地知识库的可行性，并回答以下问题：

1. 简易 Demo 能否完成文档导入、向量化、离线检索和本地资料问答链路？
2. 文件新增、修改、删除后，知识库能否正确增量更新，而不是整库重建？
3. 原文、向量、索引、日志和运行请求能否保持本地闭环，不因默认配置向外部发送数据？
4. 在典型办公 PC 上，哪些模型、切分、Top-K 和 VectorStore 组合兼顾检索质量与轻量化运行？
5. Tauri + Rust、轻量向量模型和嵌入式向量库分别适用于什么场景，有哪些限制和后续优化方向？
6. 如果后续对接苍穹 AI 或其他外部 LLM，如何划分本地检索与外部生成边界，并控制敏感数据出端？

### 0.2 不以什么为目标

- 不以“硬件升级后快了多少”为核心问题。
- 不要求四个硬件档位全部实测；必测一台典型办公 PC，有条件时增加一台低配 PC。
- 不追求跑满模型 × 切分 × Top-K × VectorStore 的全部笛卡尔积。
- 不做亿级向量、分布式并发或云向量数据库容量测试。
- 不用 Mock Embedding 推断真实检索质量。
- 不把模拟金融资料上的结果宣传为真实业务准确率。
- 不将断网可运行等同于已通过监管合规认证。

## 2. 总体评价方法

### 2.1 先验收，再排名

配置选型按以下顺序执行：

```text
目标办公 PC
  → 功能与离线闭环硬门槛
  → 增量更新正确性硬门槛
  → 质量底线
  → 性能与资源比较
  → 每类场景推荐 1–2 个配置
```

任何配置只要未通过硬门槛，就不得因为综合分较高而被推荐。

### 2.2 硬门槛

| 编号 | 硬门槛 | 通过条件 |
|---|---|---|
| G1 | Demo 基本功能 | 文档导入、建索引、检索和结果展示全部成功 |
| G2 | 完全离线运行 | 断网后核心功能可用，测试期间未发现非预期外部请求 |
| G3 | 本地数据闭环 | 原文、向量、索引、配置和日志的存储位置明确；日志不记录不必要的敏感正文 |
| G4 | 增量更新正确 | 新增可检索、修改后旧内容失效、删除后相关记录和向量清理；不影响其他文档 |
| G5 | 运行稳定 | 正式轮次无崩溃、无静默降级到 Mock、无持续换页或资源失控 |
| G6 | 质量可接受 | 达到测试前冻结的 Hit/MRR/nDCG 等质量底线 |

质量、延迟、内存和磁盘的具体数值门槛，应在正式测试前结合目标办公 PC 和课题组预期填写到测试记录中。测试结束后不得根据结果反向修改门槛。

### 2.3 软指标与推荐

通过硬门槛后，优先报告原始指标并寻找帕累托前沿：不存在另一个配置能同时做到质量更高、P95 更低、内存更少且体积更小。

最终至少给出以下推荐：

- **默认轻量配置**：满足质量底线，内存和部署体积较小，适合典型办公 PC。
- **质量优先配置**：质量提升明确，且额外资源成本在目标机器上可接受。
- **低资源兜底配置**：用于内存或磁盘受限设备；若未实测低配 PC，必须标“推测，待验证”。
- **不推荐配置**：说明被淘汰的硬门槛或成本原因。

### 2.4 综合分的边界

- 综合分不得替代原始指标、硬门槛和选型理由。
- 如确需综合分，使用测试前固定的业务权重和固定阈值归一化，不随候选集合增删而变化。
- 熵权法只可作为同一机器、同一场景内的辅助敏感性分析，不作为主结论；不得跨机器比较熵权分。

## 3. 被测系统与环境

### 3.1 必测环境

- **H1 典型办公 PC（必测）**：课题实际开发或目标办公机器。
- **H0 低配 PC（可选）**：只有取得真实机器或可复现的资源限制环境时才出实测结论。

不使用“根据核心数和内存估算其他档位性能”的结果做选型结论。

### 3.2 每轮必须记录

| 类别 | 记录项 |
|---|---|
| 硬件 | CPU 完整型号、物理核/逻辑线程、物理内存、存储介质、是否独显 |
| 系统 | Windows 版本、电源模式、是否接电、可用内存、后台任务、温度/降频异常 |
| 软件 | Git commit、构建模式、Rust、Node、Python、sentence-transformers、torch、SQLite/sqlite-vec 版本 |
| 模型 | model_id、模型文件 revision/hash、dimension、precision、normalize、pooling、max_length、prefix、config_hash |
| 数据 | dataset_id/hash、题集版本、文档数、chunk 数、chunk_size、overlap |
| 运行 | VectorStore、Top-K、batch、线程数、冷/热态、轮次、随机种子、开始/结束时间 |

### 3.3 固定运行条件

- 使用 release 构建做正式性能测试；开发模式只用于联调。
- 正式模型测试固定 CPU-only；发现 GPU 被使用时该轮作废并重测。
- 同一对比组使用相同机器、电源模式、线程配置和后台任务条件。
- 每个模型独立启动 Sidecar，避免前一个模型驻留影响后一个模型。
- 原始测试数据使用独立实验目录和数据库，不指向业务库。

## 4. 证券业务场景与测试数据

### 4.1 三类场景

| 场景 | 模拟资料 | 重点问题 | 主要验证点 |
|---|---|---|---|
| 行情/公告 | 公司公告、行情说明、事件简报 | 证券代码、公司简称、日期、数值、事件 | 精确实体与时效信息能否找到 |
| 投研 | 行业研究、公司研报、观点摘要、风险提示 | 语义改写、跨段落证据、同义词 | 长文切分和语义检索质量 |
| 交易/风控 | 交易制度、操作流程、风险规则、合规提示 | 条款、条件、例外、否定问题 | 规则类资料能否准确定位 |

资料使用公开或模拟数据，不放入真实客户信息、交易信息、内部研报或密钥。文件格式以 Demo 实际支持范围为准；未支持的格式必须列为边界，不能仅为测试结果宣称已经支持。

### 4.2 问题类型

题集至少覆盖：

- 直接关键词命中；
- 同义改写和口语化表达；
- 证券代码、公司简称与全称；
- 日期、金额、比例等数字信息；
- 跨段落或跨小节信息；
- 含否定、例外和限制条件的问题；
- 无答案问题，用于系统是否会误命中。

### 4.3 数据集分工

| 数据集 | 建议规模 | 用途 |
|---|---:|---|
| Q0 小型质量基线 | 现有 12 份模拟资料、34 题 | 保持与历史结果趋势可比 |
| Q1 场景验证集 | 约 30 份资料、至少 60 题，三场景均有覆盖 | 正式检索质量和业务适配结论 |
| P0 微基准 | 100 / 1,000 / 10,000 Chunk | 存储层延迟和规模曲线 |
| U0 增量更新集 | 固定文档集，包含可独立增删改的文件 | 文件监听和一致性验证 |

- 质量题集分为调参集和最终测试集，最终测试集不得随意修改以迎合结果。
- 性能扩容数据不得用于质量结论；重复 Chunk 只能测速度与资源。
- Q1 应为每题保存相关文档/证据段落和相关等级，并记录标注者及人工复核状态。

## 5. 配置与变量控制

### 5.1 配置身份

一条可复现的配置至少由以下字段共同定义：

```text
Model + model_version/config_hash + dimension + precision
+ chunk_strategy + chunk_size + overlap
+ Top-K + VectorStore
+ dataset_id + chunk_count + batch + thread_count
```

只写模型名称、chunk_size 和 Top-K 不足以复现结果。

### 5.2 第一阶段：单变量筛选

| 对比组 | 固定不变 | 只改变 | 输出 |
|---|---|---|---|
| 模型 | 数据、切分、Top-K、VectorStore、线程 | Model | 质量、延迟、模型体积、峰值内存 |
| 切分 | 数据、Model、Top-K、VectorStore | chunk_size 或 overlap 或策略 | 质量、chunk 数、建库时间、存储体积 |
| Top-K | 数据、Model、切分、VectorStore | Top-K | 同一个 K 下的质量与延迟 |
| 存储 | 相同向量、数据、维度、Top-K | VectorStore | 检索/写入、内存、磁盘、结果一致性 |

### 5.3 第二阶段：入围组合验证

单变量筛选后，只对 2–4 个入围配置验证关键交互：

- 轻量模型 × 固定字符/结构切分；
- 入围模型 × Top-K 3/5/10；
- fallback × sqlite-vec 在 1,000/10,000 Chunk 下的表现；
- 默认 batch 与峰值吞吐 batch 的资源差异。

这样既保留归因能力，也避免完整笛卡尔积造成无意义的工作量。

### 5.4 Top-K 口径

质量和性能必须在同一个 K 上成对采集：

| 配置 | 质量 | 性能 |
|---|---|---|
| Top-3 | Hit@3、MRR@3、nDCG@3 | Search Top-3 P50/P95 |
| Top-5 | Hit@5、MRR@5、nDCG@5 | Search Top-5 P50/P95 |
| Top-10 | Hit@10、MRR@10、nDCG@10 | Search Top-10 P50/P95 |

模型对比可统一固定 Top-3；进行 Top-K 选型时不得用 Quality@3 搭配 Search Top-10。

## 6. 测试项目

### 6.1 Demo 功能验证

| 用例 | 操作 | 通过条件 |
|---|---|---|
| F01 创建知识库 | 创建独立测试知识库 | 成功创建且路径、配置明确 |
| F02 导入文档 | 导入支持格式的模拟金融资料 | 文档数、Chunk 数与日志一致 |
| F03 建立向量索引 | 使用真实本地模型建库 | Vector 数与有效 Chunk 数一致，无 NaN/Infinity |
| F04 语义检索 | 执行三类业务问题 | 返回 Top-K、来源文档和片段可定位 |
| F05 重启恢复 | 关闭后重新启动 | 无需重新导入即可检索已有知识库 |
| F06 错误处理 | 输入错误维度、模型缺失或损坏文件 | 明确报错，不静默降级，不污染已有索引 |
| F07 本地问答链路 | 使用检索结果组装上下文 | 离线模式至少能展示证据；外部 LLM 未配置时不外发数据 |

### 6.2 离线与本地数据闭环验证

| 编号 | 验证方法 | 通过条件 |
|---|---|---|
| L01 断网启动 | 禁用网络后启动应用和 Sidecar | 应用、模型和数据库均可本地加载 |
| L02 断网检索 | 断网后导入、建库、查询 | 核心链路成功 |
| L03 外联检查 | 记录进程网络连接和请求目标 | 除明确允许的本机 loopback 外无非预期外联 |
| L04 落盘清单 | 检查应用数据、模型、数据库、日志、临时目录 | 每类数据位置和保留策略明确 |
| L05 日志检查 | 搜索正文、密钥、完整提问等敏感内容 | 未记录非必要敏感数据；必要诊断信息已最小化 |
| L06 删除残留 | 删除测试文档/知识库后检查数据库、向量和缓存 | 按设计清理，残留及原因有记录 |
| L07 失败保护 | 模型不可用或外部 AI 不可用 | 明确失败或降级到纯检索；不得自动上传资料 |

闭环验证只能证明本次实现和配置下的工程行为，不代替公司安全审查、数据分级或监管合规意见。

### 6.3 检索质量验证

优先报告以下原始指标：

| 指标 | 用途 | 备注 |
|---|---|---|
| Hit@k | 前 k 条是否至少找到一条证据 | 适合回答“能不能找到” |
| MRR@k | 第一条相关证据排名 | 适合结果首屏体验 |
| nDCG@k | 多条证据及分级相关度排序 | 需要人工分级标注 |
| Recall@k | 相关证据找全程度 | 多证据问题更有意义 |
| 无答案误命中率 | 无答案问题被错误命中的比例 | 用于发现关键词规则偏乐观 |

- 当前关键词自动判定结果与人工相关性不是同一证据等级。
- 正式报告至少抽样人工复核；Q1 若完成分级标注，以 nDCG@k 为主要综合质量指标。
- 指标本身已在 0–1 范围时，不再按候选配置做 min-max 后冒充绝对质量。

### 6.4 性能验证

| 阶段 | 主指标 | 辅助指标 |
|---|---|---|
| 应用冷启动 | 可交互时间 | Tauri/WebView2 各进程启动情况 |
| Sidecar 启动 | `/health` 就绪时间 | 启动失败率 |
| 模型冷加载 | 首次真实 Embedding 完成时间 | 峰值内存 |
| 热态端到端检索 | P50、P95 | 均值、min/max、失败率 |
| 纯存储检索 | P50、P95、QPS | 不含 Query Embedding，用于定位存储层成本 |
| 批量 Embedding | texts/s、tokens/s | batch、P95、峰值内存 |
| 初次建库 | 总时长、vectors/s | 分解为切分、Embedding、写入 |
| 增量更新 | 总时长 | 受影响 Chunk 数、阶段耗时 |

P99 不是本课题必需指标。如要报告 P99，每个配置应获得足够样本，建议至少 1,000 个热态请求；否则只报告 P50/P95。

### 6.5 资源与轻量化验证

| 指标 | 口径 |
|---|---|
| 空闲内存 | 应用稳定启动、模型是否加载分别记录 |
| 整栈峰值内存 | `max_t(local-kb + 其 WebView2 子进程 + Python Sidecar)`；不能把不同时间的进程峰值简单相加 |
| Private Bytes / Working Set | 两者分别记录，不混为同一个“内存占用” |
| CPU | 测试窗口内平均、P95、峰值，并记录逻辑 CPU 归一化口径 |
| 磁盘 | 应用 + 模型 + Python 依赖 + 数据库 + 索引的完整离线体积 |
| 换页与可用内存 | 记录系统可用内存和明显换页现象，不能只看应用 Working Set |
| 稳态回落 | 操作结束后资源能否回落，识别疑似泄漏 |

内存硬门槛优先使用“整栈峰值 + 系统保留空间 ≤ 物理内存，且无持续换页”。`peak_mem × 1.5~2 ≤ RAM` 可作为快速经验检查，但不是唯一判断依据。

### 6.6 增量更新验证

| 用例 | 操作 | 必查结果 |
|---|---|---|
| U01 新增 | 加入一份新文档 | 新 Document/Chunk/Vector 创建，新内容可检索 |
| U02 修改 | 修改一份已有文档 | 只重建目标文档；旧内容不再命中；其他文档不变 |
| U03 删除 | 删除一份文档 | Document/Chunk/Vector 按设计级联清理 |
| U04 连续修改 | 短时间内多次保存同一文件 | 最终状态正确，无重复 Chunk/Vector |
| U05 非法/损坏文件 | 导入无法解析的文件 | 明确失败且已有索引不被破坏 |
| U06 重启恢复 | 更新中或更新后重启 | 状态可恢复，未完成任务可识别或重试 |
| U07 监听降级 | 暂停文件监听后手动扫描 | 能发现并修复差异 |

每次操作前后保存 Document、Chunk、Vector 数量、目标文件 hash、Profile/Index 状态和相关 ID，用数据库查询证明一致性。

### 6.7 VectorStore 对照

fallback 与 sqlite-vec 对照应采用完全相同的向量、维度、Top-K 和数据顺序，至少比较：

- 1,000/10,000 Chunk 下的检索 P50/P95；
- 批量写入吞吐；
- 峰值内存和数据库/索引体积；
- Top-K 结果重合度、排序方向和相似度口径；
- Windows MSVC 下的扩展装载、打包、断网启动和版本兼容成本。

本课题只要求最小对照验证。若 sqlite-vec 无法稳定集成，应保留错误、版本和尝试步骤，在报告中说明“未完成本地验证”，不编造性能结果，也不为完成矩阵扩大 Demo 范围。

## 7. 统计与执行规程

### 7.1 性能样本

- 热态检索：每个配置预热至少 5 次，正式执行 3 轮，每轮至少 200 个请求；题目顺序随机化。
- 如果应用存在结果缓存，必须关闭缓存或把缓存作为独立配置记录。
- 冷启动和模型加载：每个配置至少进行 5 次独立进程启动，报告中位数和范围。
- 建库、批量 Embedding、增量更新：每个配置至少 5 次独立运行；成本过高时可降至 3 次，但需说明。
- CPU/内存采样间隔默认 500 ms；进程树必须按父子关系或本轮 PID 识别，避免统计其他 Edge/Python 进程。
- 任何失败、超时或异常都计入失败率，不得静默跳过后只统计成功请求。

### 7.2 公平性控制

- 比较配置的执行顺序随机化或轮换，避免散热和后台任务造成固定偏差。
- 冷态与热态分开，不能把第一次请求混入热态 P95。
- 同一组使用相同请求序列、数据规模和采样工具。
- 每次只改变一个变量；入围组合验证除外，但必须明确列出交互变量。
- 结果差异如果没有超过轮间波动，不宣称某配置更快。

### 7.3 每轮完整数据保存（强制）

每个正式测试轮次都必须生成唯一 `run_id`，并保存一份可机器读取、可追溯到该轮环境与配置的完整数据包。只保留终端输出、截图、P50/P95 汇总值或手工抄写表格，均不算完成数据留存。

#### 7.3.1 文件格式

每轮至少采用以下一种格式：

- **JSON**：`run_result.json`，保存元数据、逐样本数据、资源时间序列、用例结果、错误和汇总；
- **Excel**：`run_result.xlsx`，按工作表保存相同内容。

推荐同时保存：JSON 作为无损原始数据，Excel 作为人工复核和报告整理文件。若只保存一种格式，该文件也必须包含下面规定的全部数据，不能只含汇总页。无论选择哪种主格式，都额外生成 `manifest.json`，用于记录本轮文件清单和各文件 SHA-256。

#### 7.3.2 每轮目录

```text
<experiment_root>/<run_id>/
├── manifest.json            # 必需：文件清单、大小和 SHA-256
├── run_result.json          # JSON 方案，推荐作为原始真相源
├── run_result.xlsx          # Excel 方案或由 JSON 生成的复核版
└── artifacts/               # 可选：日志、网络记录、数据库检查结果等证据
```

文件内部只引用相对于本轮目录的路径，不写入用户目录等本机绝对路径。

#### 7.3.3 必存数据

| 数据区 | 必存字段 |
|---|---|
| `run_info` | schema_version、run_id、测试场景、轮次、开始/结束时间、时区、执行状态、执行命令/入口 |
| `environment` | Git commit、release/debug、Windows、CPU、核心/线程、RAM、电源模式、软件与依赖版本 |
| `config` | 完整配置身份：模型/version/hash、dimension、precision、切分、Top-K、VectorStore、batch、线程数 |
| `dataset` | dataset_id/version/hash、文档数、题目数、Chunk 数；敏感内容只保存稳定 ID/hash |
| `latency_samples` | 每个请求或阶段的 sample_id、query_id/case_id、冷/热态、开始时间、耗时、单位、成功/失败 |
| `resource_samples` | 时间戳、目标 PID/进程角色、CPU、Working Set、Private Bytes、系统可用内存；保留完整时间序列 |
| `quality_details` | 每题返回结果 ID/排名、相关性标注、Hit、RR、DCG/Recall 计算输入及该题结果 |
| `case_results` | F/L/U 用例编号、前置条件、预期、实际、通过状态和证据相对路径 |
| `errors` | 所有失败、超时、异常、退出码、阶段和错误摘要；不得只记录成功样本 |
| `summary` | 样本总数/成功数/失败数、P50/P95、吞吐、质量汇总、资源峰值、硬门槛结论 |
| `integrity` | 各数据区记录数、生成工具及版本、生成时间；文件 SHA-256 写入外部 `manifest.json` |

原始样本不得被汇总值替代；例如报告 P95 时，必须同时保存用于计算 P95 的全部有效和失败请求记录。缺失值使用 `null` 并填写 `missing_reason`，不能以空白或 `0` 代替。

#### 7.3.4 JSON 最小结构

```json
{
  "schema_version": "1.0",
  "run_info": {},
  "environment": {},
  "config": {},
  "dataset": {},
  "latency_samples": [],
  "resource_samples": [],
  "quality_details": [],
  "case_results": [],
  "errors": [],
  "summary": {},
  "integrity": {}
}
```

每个时间字段使用带时区的 ISO 8601 格式；每个数值字段明确单位，不在字段名和内容之间混用字节、MB、秒和毫秒。

#### 7.3.5 Excel 工作表

如果使用 Excel，`run_result.xlsx` 至少包含以下工作表：

| 工作表 | 内容 |
|---|---|
| `Run_Info` | run_id、时间、状态、环境和执行入口 |
| `Config` | 完整配置身份和数据集版本 |
| `Latency_Samples` | 逐请求/逐阶段耗时和状态 |
| `Resource_Samples` | CPU、内存和系统资源时间序列 |
| `Quality_Detail` | 逐题排名、相关性与质量指标输入 |
| `Case_Results` | 功能、闭环和增量更新用例结果 |
| `Errors` | 失败、超时、异常和退出码 |
| `Summary` | 汇总统计、硬门槛和推荐状态 |
| `Integrity` | 各表行数、生成工具版本和生成时间；工作簿 SHA-256 写入外部 `manifest.json` |

Excel 中的逐样本工作表不能被图表或透视表替代；图表只能作为附加展示。

#### 7.3.6 保存完成条件

一轮测试只有同时满足以下条件才记为 `COMPLETE`：

1. 主数据文件能够重新打开和解析；
2. `run_id`、环境、配置、数据集和轮次均完整；
3. 声明的样本数与实际记录数一致；
4. 成功数 + 失败数 = 总样本数；
5. 汇总值可由保存的原始样本重新计算；
6. 资源时间序列覆盖正式测试开始至结束；
7. 主数据文件生成后计算 SHA-256，并把校验值写入外部 `manifest.json`；
8. 保存失败或完整性检查失败时，本轮标记 `INVALID`，不得进入选型汇总。

写文件时先生成临时文件，完整关闭并校验后再重命名为最终文件，避免进程中断留下看似完整的半文件。

原始结果与报告分离，不提交包含真实业务资料、密钥或敏感正文的数据。查询和文档默认保存稳定 ID 与 hash；确需保存模拟文本时，应确认其中不含真实敏感信息。

## 10. 对接苍穹 AI / 外部 LLM 的边界验证

本课题核心 Demo 应在不调用外部 LLM 时完成本地文档管理、Embedding、检索和证据展示。外部 AI 只作为后续可插拔能力设计：

- 明确用户提示、数据分级、授权、审计和失败降级策略；
- 外部接口不可用时保留纯本地检索能力；
- 对接前由公司安全与合规流程确认哪些数据允许出端；
- 接口日志不得保存完整敏感上下文或密钥。

本计划只输出接口边界、风险和建议，不把未完成的外部联调写成已验证能力。

## 12. 判读边界

- Q0 的 12 份资料、34 题属于小样本，只能用于趋势对比。
- `embedding-test` 当前是 BM25 + 向量融合检索，与 `local-kb` 的纯向量检索和切分实现不同，结果不能直接互相替代。
- 关键词规则不是人工相关性标注；正式报告须说明自动评测的局限。
- 10,000 Chunk 是端侧轻量压力点，不代表生产容量上限。
- CPU-only 结果不得外推 GPU 性能。
- 内存 SQLite 微基准不能代替磁盘数据库端到端实测。
- 外部 AI 的网络时延和答案质量不进入本地检索配置的核心评分。
- 配置选择必须同时说明收益、资源代价和适用边界，不能只报一个“总分冠军”。
