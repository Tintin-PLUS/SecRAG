>
> 这是一份任务说明，不是双击或在终端中运行的程序。当前只准备了清单，下面的实验尚未执行。

## 给 Tintin 的说明

这项任务可以理解为：**给现在做好的知识库做一次有记录的体验和比较，最后说明用哪些技术比较合适，以及还有哪些不足。**

你不需要先学会所有测试代码。执行时，Codex负责检查环境、补小工具、运行实验、整理结果；你主要理解“做了什么、为什么做、结果说明什么”。

汇报可以按这六句话展开，实验结束后再填入真实结果：

1. 我先梳理了证券PC本地知识库的使用需求，明确了离线使用、资料检索和资源占用等评价重点。
2. 我复用了现有Demo，并检查了本机运行环境，统一了测试条件。
3. 我准备了模拟金融资料和一组问题，供不同方案使用相同材料进行比较。
4. 我比较了不同文字向量模型和存储方式，观察检索效果、速度及电脑资源占用。
5. 我检查了资料新增、修改、删除后的表现，并验证了能够取得证据的离线能力。
6. 我根据资料调研和实验结果，整理了技术选择建议、适用场景及后续改进方向。

## 二、执行规则

1. 先检查当前代码和环境，再实施；不要把上次检查结果当作当前已验证结果。
2. 保留现有Demo，优先复用现有代码和已下载模型；只增加实验必需的小工具和修正。
3. 可以在项目内新增脚本、测试、文档，修改必要业务代码，运行本地实验。只使用公开或模拟资料，不使用真实内部资料。
4. 不删除用户原始文件，不批量删除目录，不覆盖已有`.env`，不读取或输出密钥。不自动提交或推送Git。
5. 先利用已有依赖；缺少少量项目依赖时可安装到项目环境并记录版本。大模型下载、系统级安装、管理员操作或明显扩大工作范围时，先说明实际需要及影响。
6. 不使用外部LLM API生成测试回答，不使用真实账号和付费服务。官方资料调研可以联网，不能把实验文档内容上传。
7. 每步用普通中文说明“正在做什么”“结果说明什么”，不要贴大段代码。需要改代码时先简要解释目的。
8. 每完成一步更新下方复选框与记录。中断后从记录继续，不重做已确认完成的工作。
9. 编译通过不等于功能正确；自动生成标注不等于人工复核；设置离线参数不等于经过断网验证。
10. 不预设哪个模型或数据库最好。未测试的项目写“未测试”，失败项目保留原因，不编造数据。

## 三、按顺序完成六步

### 第一步：看看现有Demo有什么

**给用户的解释：先盘点已经做好的部分，避免重复开发。**

- [ ] 阅读README、当前架构与使用文档、相关代码以及适用的AGENTS.md。
- [ ] 检查Git状态和当前提交，不覆盖用户已有改动。
- [ ] 整理一张简单表：已有功能、尚未验证的功能、报告需要的证据。
- [ ] 建立进度文件，记下本次实际起点。

重点核实：真实模型接法、当前向量检索方式、文件变化后的更新流程、是否会调用外部AI、现有测试是否真的包含测试用例。

输出：`docs/reports/selection/01-现状说明.md`。

汇报说法：**“首先对现有原型进行梳理，确定可以直接复用的功能和需要补充验证的部分。”**

### 第二步：把这台电脑准备成测试电脑

**给用户的解释：让几种方案在相同条件下运行，比较才公平。**

- [ ] 检查Python、Rust、Node、项目依赖和本地模型，已有的正常环境不重新安装。
- [ ] 检查前端及Rust能否构建，记录真实执行的功能测试数量。
- [ ] 固定使用CPU，固定线程设置，并记录模型实际使用的设备。
- [ ] 为测试单独建立数据目录和数据库，不使用现有业务数据库。
- [ ] 记录电脑配置和软件版本；读不到的项目明确写缺失。
- [ ] 使用本地模型跑一次简单编码与检索，确认实验入口可用。

可能需要的小改动：明确让模型使用CPU，补几项计时和结果保存功能。优先增加一个简单命令行入口，直接复用Rust已有服务，不重做一套界面或另写一套检索系统。

如果现有RAG可能使用已保存的Key，本轮先只做本地检索。若验证RAG上下文，先加明确的禁止外部生成调用策略；不得依靠“猜测Key为空”。

输出：`docs/reports/selection/02-测试环境.md`。

汇报说法：**“在同一台PC上统一运行环境，固定CPU测试条件，并隔离实验数据。”**

### 第三步：准备一套模拟资料和问题

**给用户的解释：像准备一张试卷，让不同方案回答同样的问题。**

- [ ] 先准备约30份有差异的模拟金融MD/TXT资料，覆盖投研摘要、行情解读、交易流程和风险制度。
- [ ] 准备约60个问题，例如50个有答案的问题、10个资料里没有答案的问题。
- [ ] 为有答案问题标出来源文档和证据段落，问题不能只靠标题匹配。
- [ ] 留出一小部分问题用于调整设置，其余用于最终测试；两部分不要混用。
- [ ] 标记资料和答案由谁生成、是否经过人工复核。自动生成数据只能支撑“模拟场景实验”，不能代表真实公司业务准确率。
- [ ] 另生成1,000和10,000条固定测试数据用于测速度；不要把重复扩容数据当作质量评测数据。

数量是适合本次轻量验证的默认起点，不是图片验收标准。模型比较时使用相同资料与切块设置，记录输入被截断的情况。证据位置使用稳定标识，不依赖每次可能变化的数据库UUID。

输出：模拟语料、问题与答案位置清单，以及`docs/reports/selection/03-测试材料说明.md`。

汇报说法：**“构建模拟金融资料及问题集，在相同材料上评价各方案的检索效果。”**

### 第四步：做三类比较

**给用户的解释：分别比较软件外壳、理解文字的模型、保存和查找向量的方式。**

#### 4.1 软件框架：以资料调研为主

- [ ] 查阅Tauri和Electron官方资料，对比运行依赖、部署、维护、适用场景。
- [ ] 测当前Tauri应用的启动和空闲资源占用。
- [ ] 未制作等功能Electron程序时，不编造它的性能数字，也不声称当前应用已实测优于Electron。

#### 4.2 文字向量模型：复用已有模型

- [ ] 优先核实已有BGE-small和M3E-base能否作为实验候选。
- [ ] 重新核对模型官方说明、版本、输入要求和使用许可。此前M3E-base模型卡声明仅供研究、非商用，不能直接列为公司落地推荐；以执行时核对结果为准。
- [ ] 在相同资料上比较“前5条结果是否包含正确资料”、平均/较慢查询耗时、首次加载、处理资料速度和内存。
- [ ] 每个模型独立启动测试，避免前一个模型常驻内存影响后一个。
- [ ] 不预设胜者；若候选无法运行，记录原因及实际完成的对比范围。

正式热态耗时建议先预热，再执行至少100次查询请求。问题重复执行用于测耗时，不能增加质量评测的独立样本数量。统计至少包含中位数和P95；给用户解释P95为“约95%的请求都比这个时间快”。

#### 4.3 存储方式：做一个小型对照实验

- [ ] 保留现有“SQLite保存向量、Rust计算相似度”作为基线。
- [ ] 在隔离测试入口增加sqlite-vec最小适配，不要求立即替换整个Demo。
- [ ] 使用完全相同的向量和问题、相同相似度规则，比较1,000和10,000条数据的写入、查询、磁盘占用及结果一致性。
- [ ] 保持计时口径一致，例如都包含返回正文的耗时；sqlite-vec距离与当前相似度的排序方向需要正确转换。
- [ ] 核对删除和模型隔离，不只验证“能查到结果”。

如果sqlite-vec在当前环境无法完成集成，保留具体失败记录，在报告中将其标为“调研候选、未完成本地性能验证”，继续完成其余工作。不得编造存储对比结果，也不要扩展成大型数据库重构。

输出：原始测试结果及`docs/reports/selection/04-方案对比结果.md`。

汇报说法：**“通过官方资料和受控实验，从检索效果、速度、资源及部署成本等方面比较候选技术。”**

### 第五步：看看实际使用是否顺畅

**给用户的解释：检查文件变了以后知识库会不会跟着变，以及离线能用到哪一步。**

- [ ] 在专用实验目录中依次新增、修改、删除模拟文件，检查检索结果变化。
- [ ] 分清哪些更新自动完成，哪些需要点击按钮；记录从修改到新内容可检索的过程。
- [ ] 若当前仍需整库重新生成向量，先如实测量。可做小幅改造，只为变化后缺少向量的内容重新生成，并补覆盖率检查与针对性测试。
- [ ] 若自动更新需要大幅重构，本轮保留真实限制，不因第1项报告而强行扩展开发范围。
- [ ] 检查本地原文、模型、数据库、日志保存位置和外部请求路径。
- [ ] 在不影响用户当前网络和其他工作的前提下验证离线能力；不得自动关闭用户正在使用的网卡或改系统防火墙。

若没有可安全使用的隔离网络环境，先完成本地模型加载和代码路径检查，另写一个简单的手工断网验证清单。该项必须标为“待断网验证”，不能因为本地请求成功就声称完全离线测试通过。

资源占用要包含Tauri、属于该应用的WebView2子进程和Python。离线运行体积包括模型及Python依赖，不能只统计EXE。只测本机时，不声称所有低配置PC均可运行。

输出：`docs/reports/selection/05-实际使用验证.md`。

汇报说法：**“验证资料更新、本地检索和资源占用，明确原型的可用范围及尚待完善的环节。”**

### 第六步：把材料整理成报告和讲稿

**给用户的解释：把前面的记录串起来，说明为什么这样选，而不是只展示功能截图。**

- [ ] 以官方资料梳理必要的数据安全规范和模型许可，区分已有措施与改进建议，不以“本地存储”直接推导“完全合规”。
- [ ] 对苍穹AI只提出接口和数据边界建议；没有平台文档时不猜测接口或宣称已接入。
- [ ] 自动从原始结果整理表格和必要图表。
- [ ] 完成报告：任务目标、使用场景、比较方法、框架/模型/存储对比、实验结果、数据与部署边界、选型建议、限制、参考来源。
- [ ] 每条重要结论标出属于“官方资料”“代码检查”还是“实际测试”。
- [ ] 另写一份约3分钟的汇报讲稿，用“先做什么、再做什么、发现什么、建议什么”解释。
- [ ] 检查报告数字与原始结果一致，删除未经执行支持的完成声明。
- [ ] 更新进度清单，明确完成项和仍需用户协助的验证项。

输出：
